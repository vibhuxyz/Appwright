# Session 06

**Date:** 2026-10-19
**Goal of the Session:** Replace the intake flow's fixed yes/no questions with AI-generated multiple-choice questions, so the options themselves are derived from what the user's prompt leaves open, not a hardcoded Yes/No.

## What We Built

- **Multiple-choice intake questions, generated end to end from the prompt:**
  - `packages/contracts/src/session.schema.ts` — `PromptQuestionSchema` now carries `options: string[]` (2–4, refined so `defaultOptionIndex` must index into it) instead of a single `defaultAnswer: boolean`. `PromptAnswerValue` is now the chosen option's text, or `"skip"`.
  - `packages/planner/src/requirements/generate-questions.ts` — the model prompt (`buildQuestionsPrompt`) now asks for 2–4 short, product-specific answer choices per question (e.g. `"Pickup only" / "Delivery only" / "Both pickup and delivery"`) instead of a yes/no decision, with `defaultOptionIndex` as the suggested default. `parseGeneratedQuestions` normalizes and dedupes the options, drops any question left with fewer than 2 usable options, and clamps an out-of-range default index to `0`.
  - `packages/planner/src/requirements/apply-prompt-answers.ts` — `applyPromptAnswers` (builds the planner-facing prompt) and `requirementTurns` (the spoken chat transcript) now read the chosen option's text directly, falling back to the default option's text on skip.
  - `apps/web/src/features/plan/components/question-flow/` — `AnswerControls` renders one button per generated option (replacing the hardcoded Yes/No pair) plus the existing free-text input, "Help me answer", "Skip question", and "End chat" controls. `QuestionFlow`, `QuestionScrollback`, and `RequirementsPreviewPanel` read `options[defaultOptionIndex]` instead of a boolean.
- **Updated tests** in `packages/planner/test/generate-questions.test.ts` and `apps/api/test/intake-questions.test.ts` to the new options/`defaultOptionIndex` shape, including a case that drops a single-option question and one that clamps an out-of-range default index.

## New Concepts Learned

1. **A fixed boolean question is a special case of a multiple-choice one, not a different shape.**
   The whole intake pipeline — schema, model prompt, parser, prompt-builder, chat transcript, and UI — only ever needed to carry `options: string[]` + `defaultOptionIndex: number`. A strict yes/no question is just the two-option case; nothing about the pipeline had to branch on "is this yes/no or multi-choice," because there's only one shape now. This is `principle-model-the-domain` in practice: the `boolean` was encoding a domain assumption ("every open question has exactly two answers") that wasn't actually true of the product.
2. **Where an LLM-chosen default needs a second validation pass.** `defaultOptionIndex` comes back from the model as a bare number with no inherent connection to the `options` array's length. The parser treats any out-of-range or non-integer value as `0` rather than trusting the model's arithmetic — the same "fails closed, not open" posture the existing `GENERATION_FAILED` error path already used for malformed JSON.
