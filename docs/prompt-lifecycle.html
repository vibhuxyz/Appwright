What happens when you press Enter in Appwright.

One prompt crosses five processes, two data stores, a sandboxed cloud box and an LLM loop before a verified commit lands on main. This page follows it hop by hop, with the real file names.

Enter ↵
5processes: web, api, agent, Postgres, Redis
2classifier calls per prompt (api, then worker)
6tools the agent can call
6exit reasons for the agent loop
45mhard wall-clock cap per sandbox
01 · System map

Who talks to whom

The API never runs the agent. It writes a Job row and returns 202. A separate worker claims the job, boots a sandbox and runs the loop. Everything the worker does is pushed back to your browser through Redis pub/sub and the API's SSE stream.

🖥️

apps/web

React + Vite. Intake dock, chat, tabs for Code, Preview, Plan and Diff. Zustand agentStore fed by one EventSource.

🚪

apps/api

Express on :3001. Auth, rate limits, intake classifier, enqueue, SSE fan-out. Contains no agent code path.

⚙️

apps/agent

Poller claims jobs (max 3 at once). executeAgentJob owns sandbox, loop, verify, commit and merge.

📦

@repo/sandbox

E2B box (or local) with a supervisor. Egress is allow-listed to npm, GitHub and PyPI. Tools reach it only through Runtime.

🧠

agent-core

The loop, providers, prompts, project memory, pricing. Pure: no fs, no HTTP.

🗺️

blueprint + planner

Turns a big "build me X" into intent, architecture, pages, a task DAG and then runs it with retries and budgets.

04 · The agent loop

runAgentLoop, the heart of it

A while(true) in packages/agent-core/src/loop.ts. Each lap: check the budget, stream the model, run any tool calls (reads in parallel, writes one at a time), feed results back. It ends only when the model answers with no tool calls, or a limit trips.

2 · Stream modelcollectTurn → text_delta frames; 3 retries, fallback providers
3 · Bill usagecost in USD, credits decremented in one transaction

5 · Run reads ∥list_files, read_file, grep via Promise.all
6 · Run writes ›write_file, edit_file, bash, in order, abort checked between
7 · Push resultstoolResponse messages, then back to 1

RunGuard wraps every tool

  • Identical read calls return a cached result with a note
  • Refuses to overwrite a file the agent never read
  • Refuses imports of packages missing from package.json or the allow-list

Verify, then retry

  • After completed: tsc, lint, build on the worktree
  • On failure the errors are appended as a user message and the loop runs again, max 2 retries
  • Same error twice means "stuck", give up with fatalError
05 · Realtime back to the browser

Two channels, one truth

Durable state goes to Postgres as numbered Message rows. Ephemeral state (typing deltas, status, usage) goes only through Redis pub/sub. The API subscribes to session:<id> and rewrites each frame as an SSE event. If your tab reconnects, it asks for afterSeq=N and replays what it missed.

Stop button: POST /conversation/:id/stop sets a Redis cancel flag and flips the session to IDLE. The worker polls that flag every 1s and calls AbortController.abort(), and the loop returns cancelled at its next checkpoint, between tool calls.

08 · Your two screenshots, explained

Why "hy how are" sat on "Analyzing request…"

Reading the api log against the code gives this timeline for that one message.

17:33:32.6 · api

intake questions model gemini-3.7-flash. /conversation/questions starts and calls isNewAppRequest → classify().

17:33:42.7 · api · error

classify call failed: The operation timed out. That is the 10s CLASSIFY_TIMEOUT_MS. Result is provider_error, so the code uses the keyword fallback.

17:33:42.7 · api

Fallback: "hy how are" is made of greeting words (is-conversational-message.ts) and has no build verb, so it is not a new app. Action = send. The route answered 200 after 10 103 ms, which is the whole timeout.

17:33:43.1 · api

POST /conversation → 202 in 356 ms. Messages saved, worktree created, Job row inserted.

after · agent

The worker claims the job, boots a sandbox, builds the system prompt and calls classify() a second time. There is no chat shortcut in executeAgentJob, so even a greeting goes through runAgentLoop and then verify.

UI

The second line "Editing files, verifying TypeScript" is the fallback label in RunningStatusRow.tsx when the status text is not a "Running <tool>" message. It is not a real progress report.

What I would look at next (not changed): the classifier is waiting 10s on gemini-3.7-flash, so check provider latency or raise the timeout. A cheap local chat check before the LLM call, using isConversationalMessage, would skip both classify calls and could skip the sandbox for greetings. Your working tree already has uncommitted edits in is-conversational-message.ts and classify.ts heading that way.
